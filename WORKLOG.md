- **Adapt compile-cliff investigation — what worked, what didn't (2026-05-14).**  Follow-up to the `trial_batch_size` plumbing above.   - **What we tried — in order, with HLO-grounded results.**
    1. **`lax.while_loop` → `lax.scan(length=max_rounds)`** in `adjust_step_size` body.     2. **Diagnostic-carry trim** (13 → 5 element carry; diagnostics collected as `scan` ys then reduced post-loop).  Hypothesis: dtype-boundary candidates near the loop slow `loop_transpose_fusion`.  **Result: no change in compile time or HLO populations.**  **Reverted with #1.**
    3. **Python-level bisection driver** — only `_one_bisection_round` is JIT'd via `batcher.wrap_for_batch`; Python loop above the JIT boundary iterates up to `max_rounds` times with early-exit on convergence. Currently in place.
    4. **Trial-walker gather-hoist** — moved `jax.random.choice` + `tree.map(x[indices], pop)` from inside `_one_bisection_round` to a separate small JIT'd `_gather_trial_walkers` kernel (`batcher.wrap_for_batch` wrapped), called from the Python driver each round.  Body now sees `(n_samples=50, ...)` input instead of `(K=500, ...)`-with-internal-gather.  Hypothesis: matches `ns_step`'s input pattern (only the walkers being walked enter the JIT body, not the full population indexed-down-to-50 inside).  **Result: structurally correct, no measured compile-time benefit; multi-GPU hangs identically.**  Currently in place.

Already plumbed end-to-end through `AdaptationSpec` + `cli/run.py` + the four `run_ns*` sites (previous WORKLOG entry).  **Production recommendation for v6 config:** `adaptation: { trial_batch_size: 8 }`.

Neither moved the kernel populations or the compile time — XLA optimizes the gradient body identically regardless of outer wrapping or input shape.  The compile cost is dominated by the body's own HLO complexity, which is set by NeuralIL's gradient (`transpose(jvp(...))`) plus `jax.checkpoint`-driven rematerialization (off-limits per user's standing request — checkpoint is there for legitimate memory reasons on larger systems).  **Once you cannot shrink the body, the only lever is the vmap width the body operates on (`trial_batch_size`).**

  - **Persistent cache semantics — clarified for future debugging.**  When `JAX_COMPILATION_CACHE_DIR` is set, JAX caches the *post-XLA-compile artifact* (PTX/CUBIN) keyed on (jaxpr, in/out shardings, mesh, dtypes/shapes/weak-types, compiler options, JAX version).  On hit it skips XLA compile + LLVM codegen (the multi-second part) but still runs Python tracing + jaxpr→MLIR lowering every time.  This is why production runs still pay ~9 s per round-2 retrace even with `.jax_cache` populated: 9 s is trace + lower, not XLA compile.  Production's hang requires **cache miss × cold XLA compile** simultaneously — both factors at full cost.  The probe runs cold (no `JAX_COMPILATION_CACHE_DIR` set), so every call is a worst-case for XLA but a best-case for "which signatures appear at all" (no autotune state carryover).

Our 51-94 s module compiles spread across hundreds of fusion kernels, each sub-threshold.  Production hit the alarm because *one specific kernel* (`loop_select_transpose_fusion.1` with Triton-softmax operand) crossed.  That kernel's existence is gated on XLA's Triton-softmax-emitter selection, which is autotune-driven.  See the autotune-correction bullet below — the gating is in-process, not across-run.

  - **Autotune-state correction (after k125_3 cold-cache hang reproduced production hang at 21:16:50 on job 456192, `loop_add_transpose_fusion.2`).**  The k125_3 run started with a freshly-`mkdir`'d empty `.jax_cache` and still hung at the same kernel family.  All 7 cache entries were written DURING the run, not loaded.  Triton mentions in HLO (modules `0438`, `0510`, `1105` in `experiments/neuralil_si16_k125_3/hlo_dumps/456192/`) confirm XLA still emits Triton-backed kernels from a fully cold disk cache.  This corrects my earlier (wrong) claim that "Triton emitter selection accumulates across runs via the persistent compilation cache":
    - **What actually happens.**  XLA's autotuner builds state **within a single Python process** as compiles occur.  Once Triton has been benchmarked-and-picked for some softmax shape during an early `_fun` compile in the run, that decision propagates to subsequent compiles in the same process.  Persistent disk cache (`JAX_COMPILATION_CACHE_DIR`) merely serializes the *already-decided* autotune choices to disk so subsequent runs skip the benchmark; an empty disk cache does not mean the in-process autotune state is empty when the hanging compile runs.
    - **Why the probe still doesn't reproduce.**  Production performs ~10+ distinct XLA `_fun` compiles before the hanging adapt-body compile: resolver initial-energy compile, neighbor-count compile (`_recompute_max_neighbor_counts`), burn-in `_one_walk`, burn-in adapt body (multiple bisection rounds × multiple walks), post-burn-in neighbor recompute, main-NS init, main-NS `ns_step`, `ns_step` cache-hit on the second iteration, and only then the second adapt body that hangs.  Each of those compiles can teach XLA's autotuner about a Triton shape.  Our probe runs only ~2–3 compiles before adapt (backend on the K-walker pop, real `ns_step`, then the adapt body) — far too few to accumulate the same in-process autotune state.  Verified by inspecting production cold-run HLO: Triton kernels appear from module ~0438 onward; our probe's module count tops out far below that.
    - **What the probe would need.**  Either (a) an explicit warm-up phase that compiles a varied set of NeuralIL-energy + galilean-step JITs to populate autotune state, or (b) actually invoking `jaxrens.init.burn_in.initial_walk` before the target adapt call — same code production runs.  (b) is more faithful; (a) is cheaper.
